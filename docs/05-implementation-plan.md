# To-Do List 分阶段实施与维护计划

## 交付顺序

先评审设计，再通过可查看原型确认视觉和主流程，最后实现正式 Electron 应用。每个阶段有独立完成条件，避免将尚未完成的设想写成已交付能力。

## 阶段一 设计评审

本轮产出产品需求、参考产品取舍、视觉方向与设计变量、技术架构、数据与 IPC 规则、测试验收和实施计划。

已采用 A 视觉方向、列表加详情面板和 SQLite 存储，应用沿用 To-Do List 名称，并提供统一 SVG、PNG、ICO 图标。后续变更沿已确认的设计系统扩展。

完成条件为关键交互无矛盾、数据行为明确、视觉方向得到用户选择。v0 评审后的自定义窗口、选择器、折叠、旗帜、小窗和系统托盘要求已纳入同一实施范围。

## 阶段二 可查看原型

制作单个 HTML v0，呈现工作台布局、新增和编辑面板、任务完成样式、筛选与搜索位置。使用标明用途的演示任务，暴露舒展、标准、紧凑三种密度参数。

正式主窗基准为 1200 × 800，窄窗以 900 × 600 核验信息层级与控件可达性，小窗基准为 360 × 480。原型用于确认体验，生产界面使用真实持久化任务。

完成条件为用户确认视觉方向、布局、密度和关键路径。原型反馈写回 UI 文档，不把多个临时变体带进生产代码。

## 阶段三 工程基础

1. 选择并锁定兼容的 Electron、Vue、TypeScript、electron-vite、SQLite 驱动与打包依赖。
2. 建立 main、preload、renderer 和 shared 边界，启用严格类型检查与静态检查。
3. 建立独立开发、测试和正式数据目录，启用单实例与安全窗口配置。
4. 用最小验证链路确认数据库驱动在开发启动与打包后均可加载，创建记录并重启读取。
5. 建立基础迁移、错误模型、日志、测试与构建命令。

完成条件为原生 SQLite 兼容风险已经验证，受限桥接可用，生产构建能够启动。该阶段不以静态网页可访问替代 Electron 验证。

## 阶段四 核心任务闭环

实现 FR-01 至 FR-08：任务新增、编辑、删除撤销、完成切换、列表、状态筛选、持久化与反馈。

正式版引导记录按 FR-20 仅在全新生产数据库初始化时写入，一条完成、一条未完成。开发和仓储测试保持空库语义，已有数据、升级和用户删空场景不补种。

优先按一条完整垂直链路开发：新增表单、API、主进程、事务、列表回显及重启验证。之后复用边界扩展其他任务操作，避免先完成整页外观却没有真实数据。

实现草稿保护、失败保留、版本冲突和读取错误，补齐核心测试。主窗 X 直接隐藏到系统托盘并保留草稿，小窗独立关闭；只有真正退出应用才处理草稿并等待任务与备份队列。备份、迁移与恢复按可靠性案例验证，不能以一句“自动保存”替代。

完成条件为核心验收通过，安装包能稳定完成任务闭环，文档与实现相符。

## 阶段五 增强交互

按搜索、创建时间排序、优先级、手动排序的顺序实现 FR-09 至 FR-12。搜索与排序先复用纯选择器；拖拽最后加入，避免对核心列表状态造成干扰。

手动排序使用 HTML 拖放事件与独立任务列表组件，上移下移复用同一重排业务入口。拖动只在全部任务、空搜索、手动排序且无脏草稿或提交操作时启用，不将重排逻辑放入存储以外的另一套数据源。

自定义选择器、侧栏持久化、三色旗帜、小窗同步和系统托盘按最终桌面案例验收。主窗与小窗独立；快捷项只位于系统托盘右键菜单，不注册为任务栏 JumpList。

完成条件为所有启用增强功能通过组合行为、失败回滚与重启留存验证。

## 阶段六 发布与文档

发布前完成窗口缩放、中文输入法、键盘路径、字体资产许可和视觉回归检查。仅通过 package:win 生成 Windows x64 NSIS 安装包，并验证全新安装、目录选择、正常升级、原生模块加载与数据留存；中间解包目录不作为便携版交付。

补充用户操作指南、开发运行说明、目录与模块说明、数据迁移和恢复手册、验收报告及变更记录。公开分发前处理签名与渠道配置；不在未配置发布渠道时启用自动更新。

## 维护规则

### 功能变更

每项功能从业务规则开始，同时确定字段、契约、界面状态与验收条件。新增数据字段必须有默认值、迁移和旧数据测试；已经发布的迁移只追加修复，不直接改写历史脚本。

新增能力优先落在 features 下的独立模块。跨模块共享通过稳定契约完成；不从一个功能目录直接访问另一个功能的内部 store 或数据库细节。

### 设计系统

颜色、字号、间距、圆角和动效集中维护。组件按语义引用变量，例如主文字、危险操作和焦点环，不直接引用某个具体颜色名。将来添加深色模式时主要替换 token，并逐状态验证，而不是给每个组件复制一套样式。

新增表单字段复用字段、校验和错误组件。列表行、详情表单与通知各自维护，避免一个大组件承担布局、查询、数据库与生命周期。

### 数据与接口

Repository 封装任务规则与数据库事务，IPC 负责信任边界和操作排队。禁止跨层绕行。正式数据以主进程提交为准，renderer store 不再添加另一套隐藏的 LocalStorage 持久化。

契约修改时同时更新调用方、校验和测试。主进程升级与数据库迁移需要兼容策略；任务模型新增字段使用明确默认值，不依赖对象展开碰巧保留数据。

### 依赖与发布

依赖升级分开验证前端、构建工具、Electron 和原生数据库驱动。当前 better-sqlite3 13 使用 Node-API 预编译文件，重大升级后先执行 Electron 实际加载验证，再验证打包、迁移与重启；不默认恢复强制重建或更改 npmRebuild=false。锁定版本与 lockfile 一并提交，保持可复现构建。

版本记录说明实际行为变化、数据格式变化与恢复方式。升级默认保留用户数据；删除用户数据只作为独立、明确的用户操作设计。

## 后续扩展示例

- 截止日期：任务模型迁移、字段组件、元信息展示和选择器扩展，不修改 Electron 桥接安全模型。
- 标签：标签与关联表、独立标签模块和组合筛选，不改造现有任务 CRUD 的基础结构。
- 多清单：清单模型与导航上下文，任务服务补充归属校验，不让列表组件判断持久化表结构。
- 提醒：独立排程服务和系统通知适配，补充重启、休眠与权限规则，不在列表组件内维护长生命周期计时器。
- 云同步：独立评估身份、冲突、删除传播和离线策略；当前 Repository 边界有助于接入，但本地修订号本身不构成完整同步协议。

这些扩展说明现有边界如何承接变化，不表示已经排入当前功能范围。

## 主要风险与处理时机

- SQLite 预编译资源与 Electron 运行时：工程基础阶段验证实际加载，发布前再验证安装包中的原生资源。
- 草稿与其他操作覆盖：核心阶段按修订号和草稿保护案例验证。
- 搜索与手动重排歧义：增强阶段按严格启用条件和集合版本校验。
- 读取失败误清空与迁移失败：核心阶段优先完成真实数据库故障注入。
- 设计变化：按用户实际评审持续更新共享组件与设计文档，保持单层聚焦边框及自定义控件一致。
- 平台差异：首版以 Windows 真实环境验收，其他平台在对应构建机与系统补验。

## 最终完成条件

用户可以在实际 Electron 安装包中完成任务全流程，关闭后数据仍在；已实现的增强能力与组合规则一致；错误可解释、数据可恢复；开发者能够依据文档定位组件、业务规则、IPC 和数据库模块，并通过现有测试安全修改功能。
